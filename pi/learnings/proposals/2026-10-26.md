## Failure 1: Transient `000000` curl failures across all 3 watchdog targets

**Evidence:**
- `{"t":"2026-10-08T14:54:31-04:00","label":"goldenhomeproject.com",...,"http":"000000","status":"fail"}` — same timestamp also hit `meta_graph_api` and `ntfy_server` (3 unrelated services failing in the same second = local network blip, not three outages)
- `{"t":"2026-10-11T02:32:28-04:00","label":"goldenhomeproject.com",...,"http":"000000","status":"fail"}` (isolated single-cycle fail; next cycle recovered — no notification fired)
- ~70 `http:"000000"` entries in 7 days spread across all 3 targets with no pattern — classic single-shot DNS/TCP flap signature from `pi/watchdog/ghp-watchdog.sh:58`

**Root cause:** `check_one` fires one curl with no retry, so any DNS lookup hiccup or TCP SYN loss on the Pi gets logged as a failure.

**Patch:** `pi/watchdog/ghp-watchdog.sh:55-64`

```diff
 check_one() {
   local label="$1" url="$2" regex="$3"
   local code
   code=$(curl -sS -o /dev/null -w '%{http_code}' --max-time 10 "$url" 2>/dev/null || echo "000")
+  # One quick retry on connect-failure (code starts with 000) — kills single-shot
+  # DNS/TCP flaps that otherwise pollute checks.jsonl. Real outages still fail twice.
+  if [[ "$code" == 000* ]]; then
+    sleep 2
+    code=$(curl -sS -o /dev/null -w '%{http_code}' --max-time 10 "$url" 2>/dev/null || echo "000")
+  fi
   if [[ "$code" =~ $regex ]]; then
     echo "ok|$code"
   else
     echo "fail|$code"
   fi
 }
```

**Why safe:** Only adds a retry when curl already returned a connect-failure code (`000…`); successful checks are untouched, so no change to the hot path or to notification behavior for genuine outages (which still cross the 2-consecutive threshold).

**Verification:** `sudo systemctl restart ghp-watchdog && sleep 300 && grep -c '"http":"000' ~/ghp-watchdog/logs/checks.jsonl` — tail count over the next 24h should drop from ~10/day to near zero; real outages (e.g. unplug ethernet for 3min) still produce the ntfy "down" push.
