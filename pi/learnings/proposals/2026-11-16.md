## Failure 1: Watchdog logs HTTP code as `000000` (six zeros) on every curl failure

**Evidence:** 100+ occurrences in `~/ghp-watchdog/logs/checks.jsonl` this week, e.g.
- `{"t":"2026-11-14T07:38:59-05:00","label":"goldenhomeproject.com",...,"http":"000000","status":"fail"}`
- `{"t":"2026-11-14T07:38:59-05:00","label":"meta_graph_api",...,"http":"000000","status":"fail"}`
- `{"t":"2026-11-16T09:30:09-05:00","label":"goldenhomeproject.com",...,"http":"000000","status":"fail"}`

Every single failure line logs `"http":"000000"` instead of `"000"`. This is a persistent correctness bug in the only durable signal this review loop reads from — it will keep polluting future weekly reviews until fixed.

**Root cause:** `pi/watchdog/ghp-watchdog.sh:58` — on connect failure, `curl -w '%{http_code}'` already writes `000` to stdout, *then* `|| echo "000"` fires because curl exited non-zero, concatenating to `000\n000`. `$(...)` strips only the trailing newline, leaving `000000`.

**Patch:** `pi/watchdog/ghp-watchdog.sh:58`

```diff
--- a/pi/watchdog/ghp-watchdog.sh
+++ b/pi/watchdog/ghp-watchdog.sh
@@ -55,7 +55,8 @@ notify() {
 check_one() {
   local label="$1" url="$2" regex="$3"
   local code
-  code=$(curl -sS -o /dev/null -w '%{http_code}' --max-time 10 "$url" 2>/dev/null || echo "000")
+  code=$(curl -sS -o /dev/null -w '%{http_code}' --max-time 10 "$url" 2>/dev/null)
+  [ -n "$code" ] || code="000"
   if [[ "$code" =~ $regex ]]; then
     echo "ok|$code"
   else
```

**Why safe:** The regex at line 59 already rejects both `000` and `000000` (neither matches `^(2..|3..|4..)$`), so pass/fail behavior is identical before and after. Only the logged value changes. No alert thresholds, state files, or push bodies depend on the exact string.

**Verification:** `sudo systemctl restart ghp-watchdog` then `tail -f ~/ghp-watchdog/logs/checks.jsonl` and briefly block egress (e.g., unplug ethernet for 30s or hit a bogus port via a temporary `TARGETS` entry). New failure lines should show `"http":"000"`, not `"http":"000000"`.
